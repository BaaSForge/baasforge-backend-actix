# Releases

- releases must be introduced inside a chat session, so they are connected to a chat session
- the versions in releases and units are just simple int or float, int for units, float for releases, we call it `revision`, not `version`
- the releases' revisions are incremental but scoped to a chat, user a may create release 11.0 for prod or stage on chat A, then create the same on the chat B, so we have to check the chat session and be aware of the duplication there might exist
- the last live production release id is saved on the chat session when we create it (`live_production_release_id`); if production’s live release later changes to a release that was **not** produced from this session, the API exposes `stale_base_release: true`. Staging, production deploy, and unit edits **remain allowed** (units are scoped per chat). As LLMs **cannot** ship for user in any scneario (not just becuase of being stale), they only **warn** the user: a release from **this** chat is built from this session’s baseline, so when promoted it **will** replace live production and **will revert** production releases that originated in **other** chats; the user may still **intentionally** do that (e.g. rollback). A **new chat** aligned with current production avoids accidental revert unless that revert is intended
- when we create a release inside a chat, we count all release controller messages in that message and create the release revision based on it, like `15.4` if there is 6 release controller message in that chat and user clicked on the 4th and if the previous live release revision is 14.X
- user has to build an stage release before creating a production release, so the endpoint creating production release gets an stage release id
- there might be conflicts on release revisions as user can create different release on different chat sessions, so where we check release X.Y, we must be aware there might be another X.Y for the same stage or prod on another chat, that's very important
- The production release API always receive a stage release as input and convert its content into a production release. This prevents creating a production release without a corresponding stage release, and also eliminates the need to recalculate changes, since those calculations have already been done during the stage release.
- All releases (stage or prod) have a base production release which are created upon it, when a new release is created inside a chat, that release is based on the chat live release which means the last live production release when the chat has been created, if we have multiple releases inside a chat (like X.1 and X.2), they are all base on the same live prod release (X - 1 prod release)
- Everywhere in the project where only the **production release revision** (or only the **stage release revision**) is used to identify a row, you must assume the same float can exist on more than one `project_releases` row: for example revision `15.0` might be created in chat A, production reverted or superseded, then `15.0` created again in chat B. Lookups must always include **`chat_session_id` together with `revision`** (or use `project_releases.id`). Deploy APIs require both fields; revision alone is never sufficient. If multiple rows still match the same session and revision, that is an error.
- The same applies to **unit revisions** (`project_units.revision`, integer): they are scoped per chat session. The same logical unit path (`context`, `module`, `unit_type`, `unit_name_slug`) can have revision `3` in session A and again revision `3` in session B after a revert or parallel work. Any logic that compares or merges units by slugs must not treat revision numbers as globally unique—tie-break using `chat_session_id` (or full unit identity `(chat_session_id, id)`) where needed.
- **Chat session unit visibility (tools):** Each chat session is scoped to the **production release that was live when the chat was created** (`chat_sessions.live_production_release_id`), **not** the current live production release (which may have changed due to releases from other chats). All chat tools that read units (`load_latest_production_release_units`, `list_unit_contexts`, `list_modules_for_unit_contexts`) see the **effective unit set**: units from that base release, overlaid with any creates/modifies/removes made within the session itself. This means a unit created in the session is immediately visible to subsequent tool calls in the same session, and units from the base release that were modified or deleted in the session reflect those changes. Tools must never query the "current live production release" — they must use the session's snapshotted baseline.
